# 邀请内测手册（寺庙寻访向导 v0.9）

> 目标：**两周内验证「有没有人愿意用、答案能不能回到原文、会不会白跑」**。
> 不是公开推广，是 5–10 人的封闭内测。

## 一、部署（你来做，约 30 分钟）

### 1. 推代码到 GitHub

本仓库当前**没有配置 remote**，先加一个：

```bash
cd /Users/wancheng/Documents/00AIproducts/Personal-Agent-main
git remote add origin https://github.com/<你的账号>/<仓库名>.git
git push -u origin main
```

> 5 个提交已经打好（`git log --oneline -5` 可看），**我没有推送**，需要你执行。

### 2. Render 建服务

1. Render → **New → Blueprint** → 选这个仓库（会读 `render.yaml`）
2. **把 plan 从 `free` 改成付费并挂盘**（否则重启数据全丢）：
   ```yaml
   plan: starter
   disk: {name: data, mountPath: /app/data, sizeGB: 1}
   ```
3. Environment 里填（`sync: false` 的项不会自动带值）：

| 变量 | 值 |
| --- | --- |
| `DEEPSEEK_API_KEY` | 你已有的 |
| `AMAP_KEY` | 你已有的 |
| `QWEATHER_KEY` / `QWEATHER_HOST` | 你已有的（Host 带 `https://`） |
| `BOCHA_API_KEY` | 你已有的 |
| `HARNESS_ADMIN_TOKENS` | 自拟：`ops:<24位随机串>:users:read`（用来查指标） |

`AUTH_SECRET` / `HARNESS_ID_HMAC_KEY` 由 Blueprint 自动生成，不用管。

### 3. 部署后自检（必须 0 失败）

```bash
python scripts/preflight.py --base https://<你的域名> --online \
    --admin-token <上面那个 ops token>
```

失败项按提示修。常见三个：模型 key 没配（`llm=mock`）、`QWEATHER_HOST` 没带 `https://`、管理员令牌缺 `users:read`。

### 4. 恢复演练（只做一次）

```bash
python scripts/backup_data.py --keep 3     # 产出 data/backups/*.tar.gz
```
解包 → 把 `*.db` 放回 `DATA_DIR` → 重启 → 确认记忆还在。**没演练过的备份等于没有备份。**

## 二、邀请文案（可直接发给朋友）

> 我在做一个「寺庙寻访向导」，会根据你的心愿（平安/姻缘/求子/学业…）和出发地推荐寺庙，
> 每条信息都带来源链接，不吹哪座灵。
>
> 想请你帮个忙：用两周，随便问，**重点帮我试这几种**：
> 1. 我想求姻缘，从国贸出发
> 2. 妙峰山是寺庙吗？求子靠谱吗
> 3. 从我家去雍和宫怎么走
> 4. 法海寺门票多少，要预约吗
>
> 如果它给出的信息你觉得不对，点卡片右下角「资料有误？」告诉我；
> 如果它说"没查到"，也请告诉我——这说明我们该补哪条数据。
>
> 别客气，越挑刺越好。

## 六、每天 5 分钟例行（内测期间）

```bash
# 1. 指标（可追溯率/降级/时延）
python -m app.agent.temple_metrics --days 1

# 2. 有没有人报资料错（待处理列表 + 按寺庙聚合）
python scripts/triage_reports.py
python scripts/triage_reports.py --stats

# 3. 每周一次：链接抽查 + 备份
python scripts/check_links.py --only-due
python scripts/backup_data.py --keep 7
```

### 反馈处理台（`scripts/triage_reports.py`）

| 命令 | 作用 |
| --- | --- |
| `python scripts/triage_reports.py` | 看**待处理**（默认） |
| `--all` / `--status resolved` | 看全部 / 按状态看 |
| `--stats` | 按寺庙聚合：**哪座被报得最多，先修哪座** |
| `--resolve 3 --why "已按官网更新"` | 标记已处理（改完数据后执行） |
| `--reject 4 --why "核过官方，用户记错"` | 标记驳回 |
| `--export out.csv` | 导出给人工批量核对 |

**规矩：处理台只改状态、不改数据。** 改数据仍要写一次命令（`apply_open_info.py`），
这样每条修正都能追溯到具体动作，而不是"某个时间点被谁手动编辑过"。

处理一条反馈的标准动作顺序：

```bash
# 1) 核来源（打开官方页面，确认用户说得对不对）
# 2) 改数据（官方口径 / 网络口径，证据等级要选对）
python scripts/apply_open_info.py --temple 万寿寺 --open yes --closure mon \
    --method official_web --source-kind official --source <官方链接>
# 3) 标记已处理
python scripts/triage_reports.py --resolve 3 --why "按官网更正开放时间"
```

## 九 本轮推荐条件与搜索对照验证

本轮先验证条件是否真正影响选择。真实用户测试尚未执行，下面是执行方案。工程检查通过只能说明处理路径与规则符合预期。

### 先走完整任务

请参与者提供一个自己确实在考虑的北京寺庙寻访任务，自由表达需求。记录其明确提出的必要条件和偏好，再观察其从了解、比较到做决定的过程。避免先教参与者照着标准问句输入。

必要时用以下对照任务补充覆盖，每次只改变一个条件。

| 对照项 | 基础任务 | 改变的条件 | 观察结果 |
| --- | --- | --- | --- |
| 同行人 | 从同一地点出发为家人祈福 | 补充带长辈同行 | 是否优先比较较平缓的参访条件，同时避免推断老人一定不能爬山 |
| 体力约束 | 同一心愿和出发地 | 补充不爬山或少走路 | 明确冲突候选是否排除，未知项是否仍标为未知 |
| 氛围偏好 | 同一心愿和出发地 | 补充想安静一些 | 顺序和取舍是否变化，是否区分环境描述与当天人流 |
| 出行日期 | 同一组候选 | 改为有固定闭馆规则的一天 | 是否排除有明确冲突的候选，节假日或农历例外是否待核 |
| 日期澄清 | 说下周末去 | 回答周六 | 是否保留“下周”的含义并显示明确年月日 |
| 预约准备 | 选定寺庙和日期 | 问预约与买票 | 是否给出已收录规则、核实渠道，并保留实时余票未知状态 |

### 与直接搜索比较

可先用8至12位参与者作探索性试测，人数是执行建议，结果用于发现问题，不据此宣布统计显著。

每人完成两个难度接近但寺庙对象不同的任务，一个使用其平时的搜索、地图或内容平台，另一个使用本产品。交替安排方法顺序和任务，减少重复查同一寺庙带来的学习影响。两种方法使用相同设备和时间上限，试测建议每任务10分钟。参与者自行决定何时结束。

主指标采用有效决策完成率。参与者给出“去”或“不去”的决定，能说明与自身条件相关的理由，且没有漏掉已知的必要条件冲突，才计完成。“还需核实”单独记录。评分者结合来源核对理由，避免把有信心但依据错误的决定计为成功。

辅助指标采用关键信息阅读率及实际保存或分享率。阅读以观察到用户展开、阅读或在回访中准确复述相关内容为依据，滚动到底不等于读完。保存、复制到自己的记录、实际分享分别记录，口头表示愿意保存不计实际行动。本轮可人工观察记录，不要求先开发完整收藏系统。

同时记录完成耗时、仍需转到其他平台查询的内容、未完成的原因，以及哪条条件或信息实际改变了选择。只分析成功任务的耗时会遗漏失败成本，应同时报告未完成数量和时间上限。

| 匿名参与者 | 任务与方法 | 明确条件 | 是否有效完成 | 耗时或超时 | 阅读了什么 | 实际保存或分享 | 外部补查与原因 | 影响决定的信息 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
|  |  |  |  |  |  |  |  |  |

本轮整体产品与搜索的对比只能判断整体帮助。若要归因于“习俗与氛围”，需再对比资料、来源和交互一致的基础版与增加这两类内容的版本，另行准备材料。正式比较前，应根据试测基线与维护成本约定值得继续投入的最小改善幅度。

## 十 用户原始对话恢复验收

每次发布前，应在同一会话连续走完“周六去寺庙求平安，给我推荐一下 → 不用管我从哪里出发，直接给我推荐吧 → 哪个区都行 → 海淀区 → 东城区”。普通推荐先给有依据的候选，放宽位置后应继续，区域收录不足时要解释本次筛选和资料覆盖，切换区域后应恢复推荐。不能用反复要求出发地或泛称“没有资料”代替处理。

同时检查新会话、已保存旧出发地的会话、曾经回答过“没有资料”的历史会话。验收要覆盖否定、改口和放宽条件，不能只按产品示例逐句输入。推荐后的可选偏好采用自由追问或卡片问题入口，用户无需提交单选表单才能继续。
