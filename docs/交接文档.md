## 0. 三分钟理解这个项目

**它是什么**：一个面向北京寺庙的「寻访决策助手」。用户说心愿与出发地，它给出**最多 3 座可比较的寺庙**，
每座带：为什么适合、取舍、是否可上香（宗教活动场所 / 文博点 / 景区）、直线距离、开放与闭馆约束、
**每条事实的来源链接**；问口碑时给"网友怎么说"（只转述、带原文链接）；问行前时给**高德路线 + 和风天气**。

**它不是什么**（红线，写进代码与测试）：
- 不承诺祈愿结果、不给"灵验分"、不做排行榜、不编成功率
- 不代订门票 / 不代发内容 / 不代替用户对外联系
- 求子求健康只作民俗介绍，不替代医疗判断
- 查不到就说查不到，**绝不补造**

**当前完成度**（客观）：

| 维度 | 状态 |
| --- | --- |
| 功能闭环 | ✅ 对话 / 推荐 / 详情 / 对比 / 卡片 / 记忆 / 行前 / 口碑 / 指标 / 纠错 全通 |
| 工程质量 | ✅ 1894 tests、金标 42/42、评测 live 50/50、上线自检 0 失败 |
| 数据 | 30 座北京寺庙（27 可推荐）；来源 49 条全部可核；坐标 28/30 |
| 开放信息 | A 级 15 座、C 级 3 座、**未核 4 座**（法源寺/广化寺/天宁寺/云居寺） |
| 部署 | 代码已推送 GitHub，腾讯云部署包就绪，**尚未真实部署** |

## 4. 必须守住的不变量（有测试，改坏了会红）

### 4.1 证据分级：不许把二手当官方

| 证据 | method | grade | 能否升级 `sources_status` |
| --- | --- | --- | --- |
| 电话核对 | `phone` | A | ✅ |
| 政府/场所官网页面 | `official_web` + 真链接 | A | ✅ |
| 官方公众号/公告（转述、无链接） | `official_channel` | A | ✅（但 `source` 留空） |
| 旅游平台/媒体/攻略 | `media` | C | ❌ 只记录，回答里必须说"未经官方确认" |

**规矩**：`apply_open_info.py` 的 `--source` 默认 `--source-kind media`；只有 `official` 或 `--method phone` 才升级。
`open_note` 的前缀由 `--method` 决定，**不许把"网上查的"写成"电话核对"**。

### 4.2 两层依据：场所事实 ≠ 心愿说法

- `place_facts` / `basis`：可核的"这地方是什么"（哪个殿、供谁）
- `claim` + `claim_evidence`：民俗说法（"人们来求什么"）
- **殿宇有文献记载，不等于在这儿求就灵**。`basis` 只能来自官方/文献殿堂清单，不能因为"问了懂行的人"就补。
- `claim_evidence=folk` 的，回答里必须说成"民间口碑/网上说法"。

### 4.3 「平安」是默认项，不是标签

数据里**没有任何寺庙标"平安"**。用户只说平安时，检索层按「能上香 + 距离 + 氛围」给默认候选，不参与打分、不排序、不许比较灵验。

### 4.4 进不去的地方不推荐

`status ∈ {relic, closed, market}` → `wish_recommendable=false`，检索层直接过滤（有测试）。

### 4.5 不凑数

匹配不到返回空数组 + 明确提示；候选上限 3 座。**任何"补一条"的冲动都要先问：这条有来源吗？**

### 4.6 引用校验（`verify.py`）

回答生成后、发送前确定性检查：

- 回答里的 URL 必须在本次注入资料里 → 否则替换为「（来源链接未核实，已隐去）」
- 价格/时间/距离/百分比/温度**按类型分区**比对（"资料里有 20 元"不代表能写"20 公里"）
- 距离允许四舍五入（±1.5km）；行前 JSON 数字按字段名归类
- 命中写入轨迹 `citation_check`；有未出处的数字就追加「以官方公告为准」

### 4.7 性能：快照只跟改动行数有关

`app/business_stage.py` 的 `stage_business_writes()` 原来是**每节点整库快照**（495 用户时一轮 4s→18s）。
现在改成 `before_flush` 按主键记录原值 + flush 后读新值。**不要改回全表 diff**（`tests/test_staging_scaling.py` 守着）。

另有后台摘要与节点快照的握手（`background_write_window`），防止偶发 `E_NODE_FAILED`。

## 5. 四条主流程（改代码前先看懂）

### 5.1 一次寺庙对话（`app/agent/subgraphs/chat.py`）

```
用户消息
 → 隐私门 / 危机识别（优先）
 → remember_name / remember_temple_fields（心愿/出发地/同行人/出行偏好）
 → build_temple_context()   → 注入 <temple_data>（最多 3 座，带距离+依据）
 → build_review_payload()   → 只在问口碑时搜博查，注入 <review_data>
 → build_travel_payload()   → 只在问行前时调高德+和风，注入 <travel_data>
 → 模型生成（persona v5）
 → guard_text()             → 出站防泄露
 → verify_citation()        → 编造链接/数字拦截 + 追加提示
 → build_card()             → temple_card 视图模型（前端渲染）
 → temple_metrics.record()  → 可追溯率/降级/时延
```

**注意**：寺庙话题会**跳过**底座原有的通用网页搜索（`crawl_tools.source_context`）——它要真联网，实测 +15 秒。

### 5.2 数据回填（唯一入口）

```bash
python scripts/apply_open_info.py --temple 万寿寺 \
  --open yes --reservation no --closure mon --merge-closure \
  --ticket "20元（学生10元）" --hours "9:00-17:00（16:30停止入馆）" \
  --source "http://wanshousimuseum.cn/service/index.htm" \
  --publisher "万寿寺博物馆官网" --source-kind official --method official_web \
  --note "周一闭馆，节假日/寒暑假以公众号公示为准"
```

行为：来源当场 HTTP 校验（打不开就拒绝写入）→ 写入 `open_evidence` → 重生成复核清单 → 跑垂直领域测试。

### 5.3 发布前自检

```bash
python scripts/preflight.py --online          # 21 项：配置/数据/运行/外部依赖
python scripts/check_links.py --only-due      # 链接抽查（失败退出码 1）
python -m app.evals.temple_cli --mode live --sleep 0.4    # 50 条评测
python scripts/backup_data.py --keep 7        # 热备份
```

### 5.4 内测反馈

```bash
python scripts/triage_reports.py            # 待处理
python scripts/triage_reports.py --stats    # 哪座被报最多（先修哪座）
python scripts/triage_reports.py --resolve 3 --why "按官网更正"
```

处理台**只改状态不改数据**，数据改动必须走 5.2，保证每条修正可追溯。

## 9. 下一步建议（按价值排序）

### 9.1 把"可核"做成看得见的差异（半天）

卡片页脚加：「本回答引用 N 条来源，均已核对（日期）」；每条事实加「官方 / 文献 / 口碑」徽章。
理由：这是通用助手不会做的事，也是回答"凭什么用你"最直接的证据。

### 9.2 补票价（1 天）

17 座没有票价的，用官方页面核；核不到就明确写"官方未列价，以现场为准"。**不要抄 OTA。**

### 9.3 第二城（3–5 天：架构 1–2 天 + 数据 2–3 天）

**"北京"硬编码在 8 处**，必须先参数化：

1. `app/tools/travel.py` 的 `geocode(city="北京")` / `route(city="北京")`
2. `app/tools/bocha.py` 的 `city="北京"`
3. `app/agent/temple_context.py` 的正则 `北京[区县]`
4. `app/agent/domain/origins.py` 的 `BEIJING_BBOX`
5. `temples.json` / `origins.json` 的 `meta.city`
6. 工具描述与 `tool_catalog.py`（"检索北京寺庙候选"）
7. 评测用例（50 条全是北京）
8. 各处文案里的"北京"

数据侧成本远高于代码侧：一城 30 座 × 逐条核来源 + 人工复核（北京这轮从初稿到"29 条 A 级"走了 5 轮复核）。

### 9.4 行程编排（3–5 天，最大差异点）

「周六上午带父母，从国贸出发，两座寺，别爬山」→ 时间轴 + 每段交通 + 天气 + 闭馆风险 + 体力提示。
这是通用助手做不到的：它不知道哪座周一闭馆、哪座要爬山、哪座已文博化。

## 10. 协作约定（避免踩坑）

1. **改数据前先跑测试**：`pytest tests/test_temple_domain.py -q`，它会告诉你不变量是否被破坏。
2. **加工具必须三件套**：`app/tools/xxx.py` + `app/agent/tool_catalog.py` 一行 + `docs/tools.md` 一行；
   还要重生成 `tests/fixtures/main_tool_catalog.json`（否则 `test_tool_registry.py` 会红）。
3. **改提示词新建版本**（`v6.md`），不要改 `v5.md`：`tests/unit/test_prompt_files.py` 锁定版本与内容哈希。
4. **别把密钥写进代码/文档**；`.env`、`data/`、`*.db`、`.env.bak*` 已在 `.gitignore`。
5. **文档里的数字要与数据一致**：`tests/test_temple_domain.py::test_docs_stats_match_the_data` 会校验
   `docs/temple-guide.md` 的统计与 `temples.json` 对得上。
6. **提交粒度**：按"数据 / 可靠性 / 集成 / 性能 / 文档"分开提交，出问题能只回退一块。
7. **不要给用户看"看起来精确但没出处"的数字**——这是这个项目唯一的核心资产。

## 13 本轮意图与澄清修正

- 平安、顺遂、祈福作为有效需求承接。移除“没有专门求平安的寺”这类由标签设计推导现实结论的指令。
- 未提供地点的平安或就近推荐先询问大致区域；用户补充地点后沿用本次心愿。明确表示不限距离时继续推荐。
- 当前候选、选中寺庙和必要条件保存在经身份与记忆版本校验的本次对话上下文中；支持“第二个怎么样”“那里怎么去”。指代不清时确认。
- 用户明确要求就近时，候选按已有坐标的直线距离优先；平安推荐限定为资料中宗教活动场所，并过滤明确关闭条目。
- 平安推荐卡不再展示求子、财运等无关心愿条目。新增 tests/test_temple_intent_flow.py 覆盖多轮接口流程、否定纠正与对话隔离。

## 14 条件筛选与指定日期检查

- 规则实现位于 `app/agent/domain/visit_conditions.py`，日期解析位于 `visit_dates.py`。`search_temples` 接收 conditions，先排除明确体力或日期冲突，再按日期与体力信息是否充分、长辈同行、安静偏好进行比较，同一适配层内延续原来的依据或就近排序。
- 带长辈是偏好，不直接排除所有山地场所；不爬山、少走路是明确约束。缺少体力资料的候选保留“待核”，不能称为满足条件。安静依据来自已收录描述，不保证当天人少。
- 日期使用 Asia/Shanghai，支持相对日期、星期、年月日、周末澄清与条件取消。下周末回答周六仍保留下周；无效、已过或多个日期先澄清。
- 日期判断区分固定闭馆冲突、常规规则未发现冲突、需核实三类。节假日例外、农历开放日、开放时段未核实及非官方口径保留未知。当前未接法定假期或农历日历，也未查询实时预约库存。
- 预约购票指引展示已收录规则、渠道、证据等级与核对时间。只有明确的自然日提前放票规则才推算日期；开放日规则保留原口径。用户仅给日期时检查可行性，行程编排按明确请求另行处理。
- 卡片显示本次条件、适配判断与预约指引，详细依据折叠。`tests/test_temple_conditions.py` 验证单条件对照与多轮接口。
- 用户研究执行方案已补入 `docs/beta/内测手册.md` 第九节。尚未执行真人与搜索对照，不能将工程测试结果当作用户满意度证据。
