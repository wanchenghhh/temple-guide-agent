# 寺庙寻访向导（垂直领域改造说明）

> 把一个通用的「个人助理底座」改造成 **寺庙 / 许愿地寻访向导** 的垂直版本。
> 当前是 V1：数据来自公开信息并逐条标注来源与核对日期，**外部平台（小红书 / 大众点评 / 地图 / 天气）尚未接入**。

## 0. 数据可信度现状（先看这个）

| 项 | 数量 | 说明 |
| --- | --- | --- |
| 总条目 | 30 | 北京城近郊（已用大悲寺置换报国寺） |
| 可许愿 | 27 | 遗址 / 不开放 / 文化市场除外；文博点与景区可推荐但必须注明「不是上香许愿的地方」 |
| 可参观 | 28 | 与「可许愿」分开两列，避免一个「可推荐」有两种意思 |
| 来源已核 | 30 | 佛协 / 维基 / 文物局 / 佛学院 / 灵光寺官网 / 石景山区政府 / 香山公园 / 中国道教协会 / 西城区政府 / 北京数字文化馆，全部带核对日期 |

| 心愿条目 | 21 | 说法层：文献记载 12 / 民间口碑 9；其中 18 条能指向具体殿宇（场所事实） |
| 坐标 | 28 / 30 | 取自维基百科坐标接口 / 维基数据 P625；云居寺、和平寺取不到 → 留空 |
| 常见出发地 | 14 | 国贸、五道口、西二旗、望京、中关村、天通苑、奥林匹克公园、三里屯、北京南站、北京西站、首都机场、通州北苑、苹果园、石景山游乐园 |
| 开放状态 | 官方明确 8 座 | 其余仍标「未核实」——公告之外不猜（详见清单「开放约束」列） |

四条硬规矩（有测试守着）：

1. **没有真来源就不写成事实。** `sources_status` 只能是 `verified`（真 URL + 核对日期）或 `unverified`（空数组）。占位文案一律违反测试。
2. **依据分两层。** `place_facts` 是「这地方是什么」（可核，必须带 URL）；`wish.claim` 是「人们来求什么」（民俗用法）。**殿宇有文献记载，不等于在这儿求就灵**——两层各带自己的证据等级。
3. **公众号只当渠道。** 微信公众号无法程序核验（要登录、链接不稳），只能进 `finder_hint`（去哪问），不进 `sources`。
4. **进不去的地方不推荐。** 遗址、不开放、文化市场 `wish_recommendable: false`，检索层直接过滤。
5. **场所类型分三种，不能混。** 宗教活动场所（能上香）／文博点（博物馆）／景区·民间信仰（如妙峰山，无僧道进驻）。
   `religious_registered` 用 True/False/None（None=待核），不猜。

## 1. 一句话

用户说「我想求姻缘，从国贸出发」——它记住你的心愿和出发地，从北京 30 座里挑最多 3 个可比较的选择，
说清**哪座殿、供的是谁、说法属民俗还是文献、有什么取舍**，再给详情与行前提示；
**不吹哪座最灵、不编数据，查不到就说查不到。**

## 3. 数据结构（schema v3）

```
temples[]
  id / name / aliases / district / sect
  status          religious_site | heritage | scenic | relic | closed | market
  religious_registered  是否登记宗教活动场所（True/False/None=待核）
  visitable       能不能去参观
  wish_recommendable  能不能作为许愿推荐（硬门）
  open_status     normal | reservation | unverified | closed
  closure_rule    ["周一闭馆"] 等会让人白跑的约束
  place_facts[]   场所事实：文本 + 出处 URL + 核对日期（可核）
  halls[]         殿名 + 神像 + 相关心愿 + 出处
  wish_themes[]   theme + role + claim（民俗说法）+ claim_evidence（reference/folk）
                  + basis（哪个殿）+ basis_source
  finder_hint[]   去哪问：公众号/官网名（**不是**来源）
  sources[]       真 URL + 发布方 + 核对日期（或空数组）
  sources_status  verified | unverified
  checked_at      核对日期
```

### 「平安」为什么不在数据里

30 座里 29 座标「平安」，等于没筛。现在「平安」是**默认项**：用户只说平安时，
不参与匹配打分、不参与排序，只按「可进 + 近 + 氛围」给候选，并明确说「没有专门求平安的寺」。

### 为什么要把依据拆成两层

上一版的错误是「殿宇有记载 → 就说在这儿求 X 灵」。拆开之后：

| 层 | 例子 | 能不能核 |
| --- | --- | --- |
| 场所事实 | 孔庙大成殿供孔子；东岳庙西路有月老殿 | 能（文物局/百科，带 URL） |
| 许愿说法 | 民众到孔庙求考试顺利；到月老殿求姻缘 | 民俗，只能说「民间说法」 |

孔庙的「学业」因此仍是 `folk`：祭孔是文献事实，求学业是民俗用法，不升格。

## 5. 距离口径（新）

* **只算直线距离**，措辞固定为「距国贸直线约 7.2 公里（非行车距离）」——行车时间要看路况，不冒充。
* **排序：依据强度优先，距离只在同分时起作用**。「平安」这类默认项先按「能不能上香」分组，
  再在同类里按距离排——否则从五道口出发最近的三座全是大钟寺、五塔寺、万寿寺（都是博物馆）。
* **没有坐标就不算**：出发地不在 14 个地标里、或寺庙没有坐标时，返回 `None` 并直接告诉用户
  「我这边没有坐标，只能按区县给你排」，绝不估一个数字（有测试守着）。

## 6. 检索规则（值得记住的三条）

1. **具体心愿只认有说法的寺庙。** 姻缘 = 5 座，每座都挂着「哪个殿 + 说法类型」；
   「备注里出现关键词就算命中」的模糊兜底已删除（它曾让「健康」虚胖到 4 座）。
2. **能上香的排前。** 同样有说法时，活跃寺院优先于文博点——因为文博点不能上香。
3. **匹配不到就返回空。** 候选不足不凑数，也不补造寺庙。
4. **用户说简称也要认。** 孔庙 / 国子监 / 火神庙 / 石刻博物馆 / 玲珑塔 都能对上（有测试）。

## 7. 顺手修掉的一个真实 bug

**现象**：连续对话时偶发 `E_NODE_FAILED`（寺庙话题约 1/5 概率）。

**根因**：每个节点在「私有快照」里写库，最后按行做乐观校验再发布；
后台的对话摘要线程会写同一行 `user_profiles`。当摘要在「快照 → 发布」窗口里提交，
乐观校验判定为并发冲突，整个节点 fail closed。

**修复**：staging 窗口与后台写入做一次握手（`app/business_stage.py` 的
`background_write_window` / `_enter_staging`），并且窗口从**拍快照之前**就开始。
语义不变（仍然 fail closed，绝不覆盖并发写），只消除了误报窗口。
**回归测试**：`tests/test_business_stage_handoff.py`（4 条）。

## 9. 可信度闭环（本轮新增）

两件事把「不编造」从口号变成可检验的动作。

### 引用校验（`app/agent/domain/verify.py`）

回答生成后、发送前跑一遍，确定性、不调模型：

| 检查 | 规则 | 处理 |
| --- | --- | --- |
| 链接白名单 | 回答里的 http(s) 链接必须出现在本次注入的资料里 | 编造的链接直接替换为「（来源链接未核实，已隐去）」 |
| 风险数字 | 价格（元）、时间、距离（公里）、百分比，必须能在资料里找到同一个数字 | 标记 + 追加「以官方公告为准」，并写进轨迹 `citation_check` |
| 未核实来源 | 资料本身标 `unverified` 时记一笔 | 进轨迹，方便统计 |

限制（写清楚，别自欺）：这不是语义校验，抓不到「把 A 殿的说法安到 B 殿」。那种只能人工抽查。

### 每月链接抽查（`scripts/check_links.py`）

```bash
.venv/bin/python scripts/check_links.py              # 全量（70 条，约 30 秒）
.venv/bin/python scripts/check_links.py --only-due   # 只查超 30 天没核的
.venv/bin/python scripts/check_links.py --write-status  # 把结果写回数据的 link_status
```

* HEAD 失败会自动用 GET 复核——政府站常见 HEAD 返 404、GET 返 200，只看 HEAD 会误报；
* 报告写到 `docs/link-check-report.md`，含「失效清单 + 处理方式」；
* 有失败就退出码 1，cron / CI 能发现。

## 10. 结构化卡片（本轮新增）

以前回答是一坨文字，现在同一份资料会渲染成卡片：

| 卡片 | 触发 | 内容 |
| --- | --- | --- |
| `temple_recommend` | 用户说心愿/区域 | 最多 3 座，每座：序号 + 名称 + 区县 + 场所类型 + 直线距离 + 心愿（含殿宇与「民间口碑/文献记载」标签）+ 开放提示 + 闭馆约束 + 可点来源 |
| `temple_detail` | 指定一座寺 | 单座详情；**不会**把记忆里的旧心愿贴到这张卡上 |
| `temple_compare` | 一次提两座（如「红螺寺还是妙峰山」） | 两座并排 |

三条约束（有测试守着）：

1. **卡片不新增事实**：字段全部来自本轮注入的资料；
2. **口碑要标**：`folk` 的条目在卡片上带「民间口碑」标签，文博点会带「不是上香许愿的寺院」提示；
3. **不骗人**：没有坐标就不显示公里数，没有来源就写「暂未核实」，页脚固定说明「直线距离（非行车距离）」+「临行复核」。

后端字段在 `/api/chat` 响应的 `data.temple_card`；前端在 `static/js/flows.js` 的 `emitTemple()` 里入列，刷新后从本地记录恢复。

## 11. 博查搜索（评价摘要的地基，默认关闭）

`web_search_bocha` 是只读工具，为后面「公开评价摘要」和「链接失效找替代源」准备。

| 约束 | 做法 |
| --- | --- |
| 内容边界 | 只取标题 / 摘要 / 链接 / 站点 / 发布时间；摘要截断 200 字，**不落正文** |
| 可信度 | 结果统一 `trust=untrusted_source_data`；分享类站点标 `kind=ugc`，回答里必须说「网友说法」 |
| 成本 | 同一 query 缓存 12 小时；`BOCHA_DAILY_CAP`（默认 200）每天到点即停，用量写 `DATA_DIR/bocha_usage.json` |
| 开关 | `BOCHA_ENABLED=1` 才启用，默认关闭 |
| 跑题过滤 | 实测搜「法海寺」会返回杭州「法喜寺」；命中必须含寺名/别名，否则丢弃并记 `dropped_off_topic` |

```bash
BOCHA_ENABLED=1 python -c "
from app.tools import bocha
r = bocha.search_for_temple('妙峰山', '求子')
print(r['count'], r['dropped_by_name'], r['dropped_by_theme'])
"
```

实测（2026-11-07）：

| 查询 | 保留 | 名称剔除 | 心愿剔除 | 说明 |
| --- | --- | --- | --- | --- |
| 妙峰山 / 求子 | 3 | 0 | 2 | 留下「妙峰山 求子求健康」「贴吧：北京妙峰山求子」等 |
| 白云观 / 求子 | 1 | 0 | 4 | 只留「白云观 送子娘娘殿 求子」那条 |
| 法海寺 / 姻缘 | 0 | 0 | — | 法海寺没有姻缘话题 → 返回 0，由回答如实说「没找到相关分享」 |

> 关键设计：**搜不到就返回 0**，不拿游记凑数。这比「有 3 条但都无关」诚实得多。

## 12. 公开分享摘要（评价层，已接进回答与卡片）

问口碑时（`评价/口碑/怎么样/灵不灵/有人说过吗…` + 指名寺庙）才去搜，搜到的东西按三层过滤：

```
博查搜索 → ① 名称过滤（必须是这座寺）→ ② 八卦过滤（明星上香新闻不算口碑）
        → ③ 心愿过滤（摘要里没提这个心愿就丢）→ 最多 3 条
```

实测（2026-11-07，真调用）：

| 查询 | 保留 | 八卦剔除 | 心愿剔除 | 结果 |
| --- | --- | --- | --- | --- |
| 妙峰山 / 求子 | 3 | 0 | 2 | 头条亲历贴、墙根网攻略、贴吧帖 |
| 白云观 / 求子 | **0** | 1（张兰上香新闻） | 3 | 返回空，回答如实说没找到 |

### 三层护栏

1. **不可信**：注入块带 `untrusted_source_data` 规则；摘要截断 200 字，去平台样板文字（"展开 不感兴趣 举报 扫码下载APP…"）。
2. **只转述**：`灵验/很准/一定成/保证` 这类断言若出现在回答里且没有「网友说」等转述标记，记一笔 `review_claim` 并强制追加免责；
   有分享时**固定**追加「以上是网友公开分享，不是事实陈述，也不代表祈愿结果。」
3. **可回溯**：卡片「网友怎么说」区每条带站点 + 日期 + 原文链接，`ugc` 站点（头条/贴吧/小红书…）带标记。

前端：`static/js/cards.js` 的 `templeReviews()`；接口字段 `/api/chat` → `data.temple_card.reviews`。

## 13. 两个性能/运维坑（本轮实测发现）

### 通用网页搜索会拖慢 15 秒

寺庙话题原本会走底座的 `source_context()`（真联网搜网页）。实测一次 **+15 秒**，
把「5–10 秒出答案」直接打破，还会把不可信网页塞进提示词。

**修法**：有策展资料时**跳过**通用搜索（`chat.py` 里 `temple_payload is None` 才走）。
效果：`红螺寺怎么去` 从 **18.5s → 2.5s**。

### 本地库变大后每轮变慢

`prepare_workspace()` 每个节点要把业务库整库快照一次。本地评测攒了 495 个临时用户后，
一次对话从 4 秒涨到 18 秒。清理后回到 3 秒左右。

```bash
python scripts/prune_eval_data.py            # 预览（默认不删）
python scripts/prune_eval_data.py --yes      # 真删 + VACUUM
```

> 这是**上线前必须处理的结构性问题**：真实用户增长同样会让每轮变慢。
> 方向：快照只覆盖本轮可能写的表，或改成按行快照 + 增量应用（已记入 roadmap 步骤 8/9）。

## 14. 指标、纠错与性能（步骤 8）

### 领域指标（每天该看的几个数）

`GET /api/admin/temple/metrics?days=7`（需要管理员令牌，`users:read` 权限）：

| 指标 | 含义 | 上线门槛 |
| --- | --- | --- |
| `traceable_rate` | 引用校验通过的轮次占比 | **编造一条即不算过关** |
| `degraded_rate` | 降级轮次（资料缺、来源未核、搜索不可用、额度用完） | 越低越好 |
| `candidate_short_rate` | 候选不足 3 座的推荐轮次 | 观察项（不凑数是设计） |
| `review_turns` | 带公开分享的轮次 | 观察项 |
| `latency_p50/p95` | 时延 | PRD 目标 5–10 秒 |
| `cost_per_turn` | 单轮成本 | 几毛以内 |

只存聚合数字，**表里没有 user_id、没有问题、没有回答**（有测试守着）。

命令行：`python -m app.agent.temple_metrics --days 7`

### 数据纠错入口

* 用户端：卡片底部「资料有误？」→ 填一句描述 → `POST /api/temple/report`
* 只存 寺名 / 字段 / 描述，**不存身份**；同一条重复提交会去重
* 运营端：`GET /api/admin/temple/reports`

### 性能：把 O(全库) 改成 O(改动行数)

原来每个节点要在开始和结束各把业务库全表读一遍做 diff。实测灌到 3000 个用户后，
一次对话从 3.6 秒变成 18 秒——**用户越多越慢，上线必炸**。

改成在 `before_flush` 里按主键记录「原值」，flush 后再读「新值」：

| 场景 | 改前 | 改后 |
| --- | --- | --- |
| 500 用户 | ~4s | ~4s |
| **3000 用户** | **~18s** | **~3.6s**（与库大小脱钩） |

回归测试 `tests/test_staging_scaling.py`：0 行 vs 3000 行无关数据时，按主键读取次数必须相同。

## 15. 行前准备（高德 + 和风，已接真实数据）

问路线/天气时才请求（`怎么去 / 多久 / 多远 / 地铁 / 自驾 / 天气 / 明天` + 指名寺庙）。

| 能力 | 实现 |
| --- | --- |
| 出发地定位 | 先查 14 个常见地标；不认识就走**高德地理编码**（实测「三里河南边」→ 三里河） |
| 路线 | 高德公交/驾车/步行路径规划，取方案数与耗时；出行方式从问句里判断 |
| 天气 | 和风 3 天预报，按用户说的日期挑（今天/明天/后天/3月5号）；超出范围**明确说查不到** |
| 缓存 | 路线 6 小时、天气 3 小时、地理编码 30 天 |
| 额度 | `TRAVEL_DAILY_CAP=300` 每天到点即停，用量写 `data/travel_usage.json` |
| 失败 | 接口异常/额度用完/定位失败 → 注入「查不到」，模型不许自己估算 |

卡片上多一块「行前信息」：`路线 公交/地铁 · 约 8.1 公里 · 约 46 分钟 · 数据时间` +
`天气 2026-11-09 · 晴 · -3~12℃ · 西南风1-3级 · 数据时间`，页脚固定「接口给的预计值，出发前请再查一次」。

> 顺手修了引用校验的一个误判：行前数据是 JSON 数字（`distance_km`/`temp_max`），
> 原来只认「X 公里」文本，导致**真实数据被标记成编造**。现在按字段名归入「距离/温度」池子比对。
