## 4. 落地脚本的 7 个硬伤（这才是真正会污染数据的地方）

以下对应 `scripts/apply_open_info.py` 与 `scripts/render_call_sheet.py` 的实际代码：

1. **`--source` 只验 HTTP 200，却硬编码 `kind: "official"`**（第 101–112 行、`_check_url` 第 49–59 行还接受 3xx）。
   → 传一个能打开的携程/百科/攻略链接，数据里就会多出一条「官方来源」，并把 `sources_status` 置为 `verified`。这与项目反复声明的「未核实字段一律标 unverified、公众号只能当渠道不能当引用」**直接冲突**。
   **改法**：新增 `--source-kind official|media|folk` 与 `--method phone|official_web|media`；只有 `official`/`phone` 才能升级，默认 `media`。
2. **核对单的说明有误导**：当前 `temples.json` 里 **30/30 条 `sources_status` 已是 `verified`**，22 座 `open_status` 全是 `unverified`。给 `--source` 只影响「来源」，**不会让开放信息变得可信**——`open_status` 是由 `--open` 决定的，两者是完全独立的维度。建议新增 `open_verified_at` / `open_evidence` 字段，别复用 `sources_status`。
3. **`--open` 与 `--reservation` 语义打架**：`OPEN_CHOICES` 把 `reservation`（必须预约）和 `yes`/`no`/`limited` 并列成单一 `open_status`，同时又用 `--reservation` 写进 note。于是「正常开放**且**必须预约」（卧佛寺、潭柘寺、云居寺）无法表达；`--open reservation --reservation no` 还会写出自相矛盾的 note。建议 `open_status` 只留 `normal/closed/unverified`，预约拆成独立布尔字段。
4. **`--closure` 枚举覆盖不了现实**：只有 `none/mon/mon-tue/first-lunar/winter`（文档还漏写了 `winter`）。表达不了「周一闭馆（法定节假日除外）」「暑期临时改周二」「淡旺季切换」「法会/庙会调整」「冬季防火闭园」——而这些恰恰是本次核实里最常见的规则。且第 97–99 行 `temple["closure_rule"] = closure` **整体覆盖数组**，会抹掉已有规则。建议改为增量合并，并把例外说明放进 `open_note`。
5. **`_open_note()` 第 63 行硬编码「电话核对（{date}）」**。本次是资料核查，若照命令落地，会把「网上查到的」写成「电话核对」，属于伪造证据来源。应由 `--method` 决定前缀。
6. **`checked_at` 一词三用**（第 118 行统一覆盖）：数据里它同时承担「链接核对日」「坐标核对日」「开放信息核对日」，而 `check_links.py` / 链接抽查报告又按它判断到期，容易被一次开放信息更新污染链接抽查节奏。
7. **附录方法论错误**：`_pending_claims` 生成的提示是「找懂行的人问一句就能补上」「确认后补 `basis`」。民俗说法**不会因为问了人就变成场所事实**；`basis` 只能来自 A 级殿堂清单，且 `claim_evidence` 应固定为 `folk`。建议改成「若无 A 级殿堂依据，保持 `basis` 为空，回答里标注民间说法」。

> 优先级建议：先修 1、2、5 再落地任何数据；否则这轮核实做得越细，写进 `temples.json` 的「伪官方」痕迹越多。

## 7. 落地时的两条硬规矩

1. **只把 A 级官方 URL 传给 `--source`**（市政府/委办局、区政府、场所官网/官方公告、市佛协、公园名录）。B 级北京旅游网、媒体转载、C 级 OTA/百科**一律不要传**——否则脚本会把它们标成 `official`。
2. **本次是资料核查，`--note` 不要写「电话确认」**。在脚本增加 `--method` 之前，建议在 note 里显式写「联网资料核查 2026-11-09，未经电话确认」，避免 `open_note` 出现「电话核对」字样。
